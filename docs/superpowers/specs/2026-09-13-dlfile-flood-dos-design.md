# Дизайн: защита файлового потока netchan от DoS через флуд `dlfile`

- **Issue:** [rehlds/ReHLDS#1200](https://github.com/rehlds/ReHLDS/issues/1200) — [DoS] Server freeze via `dlfile` flood when `sv_allowdownload 1` and `sv_downloadurl ""`
- **Дата:** 2026-09-13
- **Статус:** согласован с пользователем; фидбек мейнтейнера учтён (лимит — в нетчане, на уровне загрузки файла)

## 1. Проблема

Когда `sv_downloadurl` пуст и `sv_allowdownload 1`, сервер сам раздаёт файлы по команде клиента `dlfile <имя>`. Подключающийся клиент может заваливать сервер повторными `dlfile`-запросами больших файлов (спам-цикл + speedhack): FPS сервера падает до ~0, все игроки получают 1000+ пинг, сервер не отвечает, пока флуд не прекратится.

## 2. Анализ кода (root cause)

Путь запроса: `SV_BeginFileDownload_f` (`engine/sv_main.cpp:7997`) → `Netchan_CreateFileFragments` / `Netchan_CreateFileFragmentsFromBuffer` → очередь `netchan.waitlist[FRAG_FILE_STREAM]` → отправка в `Netchan_FragSend` / `Netchan_Transmit`.

Два вектора прожига CPU:

1. **Файловый путь (обычные ресурсы).**
   - Каждый `dlfile` безусловно ставит ещё одну копию файла в `waitlist[FRAG_FILE_STREAM]` — очередь растёт неограниченно (в repro — 2000 копий `cs_dust.wad`).
   - Без `REHLDS_FIXES` каждый запрос проходит тяжёлый путь целиком: открытие файла, bz2-сжатие level 9, нарезка на чанки — и только последующий `Netchan_FragSend` видит, что очередь занята. «Пакует, и только потом понимает, что очередь занята».
   - С `REHLDS_FIXES` запрос ставит дешёвую заглушку (stub), но каждая копия из очереди после завершения предыдущей передачи разворачивается заново в `Netchan_FragSend` (`net_chan.cpp:901`): чтение `.ztmp` (мегабайты), ~тысячи аллокаций `fragbuf_t`, O(n) проход waitlist. При разгоне клиента (`rate` не ограничен, `sv_maxrate` по умолчанию `0`; каждая передача завершается мгновенно) развороты идут конвейером и насыщают main thread.

2. **Буферный путь (`!MD5…`, кастом-спреи).** Быстрого stub-пути нет вообще: каждый запрос = `HPAK_GetDataPointer` (диск) + `BZ2_bzBuffToBuffCompress` level 9 (`net_chan.cpp:1122`) + постановка полной цепочки чанков в ту же очередь.

Состояние клиента при этом не ограничено ничем: ни лимита одновременных передач, ни лимита очереди, ни дедупликации повторных запросов.

## 3. Требования к совместимости (проверено по коду реального клиента)

Клиентская логика GoldSrc (`CL_BatchResourceRequest`, `CL_CheckFile`):

- Клиент шлёт `dlfile` **батчем** — сразу для всех отсутствующих ресурсов одним сообщением. Повторные запросы одного файла легитимны (дедуп на клиенте есть только для декалей — флаг `RES_REQUESTED`; приход `svc_customization` повторно вызывает `CL_BatchResourceRequest`).
- Поэтому **нельзя**: вводить «строго 1 загрузку на клиента», интервалы/троттлинг между запросами, тихо терять запросы — это ломает легитимный батч.
- Обработка `svc_filetxferfailed` у клиента штатная: файл пропускается, соединение продолжается (как при любом фейле скачивания).
- Сервер физически отдаёт файлы строго последовательно — файловый поток один (`FRAG_FILE_STREAM`).

## 4. Решение

Политика допуска — в нетчане, на уровне очереди файлового потока (`net_chan.cpp`), единообразно для файлового и буферного путей.

**Семантика возврата (единая конвенция):**

| Ситуация | Возврат | Действие |
|---|---|---|
| Файл уже передаётся (in-flight) или стоит в очереди | `TRUE` (успех) | Ничего не ставить. Повторный запрос удовлетворяется уже идущей передачей; ответ не отправляется. |
| В очереди уже `MAX_QUEUED_FILE_TRANSFERS` запросов | `FALSE` | Ничего не ставить. Вызывающий отправляет `SV_FailDownload` → клиент пропускает файл. |
| Обычная постановка | `TRUE` | Как сейчас. |

### 4.1 Новые элементы (`engine/net_chan.h`, `engine/net_chan.cpp`)

```cpp
// net_chan.h
const int MAX_QUEUED_FILE_TRANSFERS = 32;

qboolean Netchan_IsFileTransferActive(netchan_t *chan, const char *filename);
int Netchan_CountQueuedFileTransfers(netchan_t *chan);
```

- `Netchan_IsFileTransferActive` — `TRUE`, если `filename` (без учёта регистра) совпадает с файлом in-flight (голова `chan->fragbufs[FRAG_FILE_STREAM]`) или стоит в очереди (проход узлов `chan->waitlist[FRAG_FILE_STREAM]`, сравнение `node->fragbufs->filename`).
- `Netchan_CountQueuedFileTransfers` — число узлов-запросов в `chan->waitlist[FRAG_FILE_STREAM]` (узел = один запрос: stub или цепочка чанков).
- Функции не `static`: юнит-тесты вызывают их напрямую на вручную собранном `netchan_t`.
- Значение 32: реальный ресурс-лист карты — единицы-десятки файлов, 32 покрывает легитимный батч с запасом; при флуде очередь ограничена 32 вместо ∞.

### 4.2 `Netchan_CreateFileFragments` (серверная ветка)

После существующих проверок `FS_FileExists`/размера, до аллокации stub'а:

```cpp
if (Netchan_IsFileTransferActive(chan, filename))
    return TRUE;   // дубликат файла, который уже качается
if (Netchan_CountQueuedFileTransfers(chan) >= MAX_QUEUED_FILE_TRANSFERS)
    return FALSE;  // очередь переполнена
```

Существующий вызов в `SV_BeginFileDownload_f` уже трактует `== 0` как `SV_FailDownload` — код обработчика для этого пути не меняется. Клиентская ветка (`!server`) не затрагивается. В сборке без `REHLDS_FIXES` (публичная функция = тяжёлый путь) проверки ставятся в её начале (`if (server && …)`).

### 4.3 `Netchan_CreateFileFragmentsFromBuffer` (путь `!MD5`)

- Сигнатура `void` → `int` (возвращает `TRUE`/`FALSE` по конвенции выше). Функция движково-внутренняя: объявления только в `net_chan.h`/`server.h`, вызовы только `sv_main.cpp:8068,8079`, в plugin API не экспортирована, ABI (`CreateInterface`) не затронут.
- Проверки дедупа/лимита — в начале функции, **до** `BZ2_bzBuffToBuffCompress` и чтения HPAK: закрывает второй вектор DoS.
- Попутно чанкам проставляется `buf->filename` (сейчас не проставляется) — дедуп единообразен для обоих путей.

### 4.4 `SV_BeginFileDownload_f` (!MD5-ветка — единственное изменение обработчика)

```cpp
if (!Netchan_CreateFileFragmentsFromBuffer(TRUE, &host_client->netchan, name, pbuf, size))
    SV_FailDownload(name);   // очередь переполнена — клиент пропустит файл
else
    Netchan_FragSend(&host_client->netchan);
```

## 5. Эффект

- **2000×`dlfile cs_dust.wad`:** первый запрос ставит файл, остальные 1999 отсекаются дедупом за O(32) сравнений строк — без аллокаций, повторных «упаковок» и роста очереди. Разворот в `Netchan_FragSend` — максимум 1 файл + ≤32 запроса, проход waitlist O(32) вместо O(2000).
- **2000×`dlfile !MD5…`:** дедуп по имени; разные хеши — до 32, дальше `FALSE` без чтения hpk и сжатия.
- Легитимный клиент: батч любого реального размера проходит без изменений; повторные запросы качающегося файла обрабатываются молча (так и было бы по смыслу).

## 6. Что осознанно не делаем

- Никаких новых cvar и новых полей в `client_t`.
- HLTV (`HLTV/common/BaseClient.cpp`, `CMD_DownloadFile`) — отдельная кодовая база, вне скоупа issue.
- Plugin API / hookchains не затрагиваются.
- Троттлинг по интервалу, «строго 1 загрузка», тихое игнорирование переполнения — отвергнуты как ломающие легитимный батч (см. §3).

## 7. Тесты и верификация

1. **Юнит-тесты** (`unittests/download_tests.cpp`, CppUnitLite): на вручную собранном `netchan_t` (zeroed + ручные stub-цепочки, без FS):
   - дедуп: файл в очереди / in-flight / отсутствует;
   - `Netchan_CountQueuedFileTransfers`: 0, N, границы;
   - лимит: 32-й запрос проходит, 33-й — `FALSE`.
2. Регресс: полный прогон юнит-тестов (exit code 0/3 — норма), сборка `./build.sh --compiler=gcc --jobs=$(nproc)` → `build/rehlds/engine_i486.so`.
3. Мануально по repro из issue: спам-цикл `dlfile cs_dust.wad` (2000 повторов + speedhack) → FPS сервера стабилен, сервер отвечает; отключение флуда не требуется для восстановления.
4. Регресс-проверка скачивания: клиент без 2-3 ресурсов (wad/модель/спрей) подключается к серверу с пустым `sv_downloadurl` — все файлы скачиваются, включая повторные запросы.

## 8. Риски и открытые вопросы

- Экзотические клиенты, ставящие в очередь >32 файлов одновременно: получат `filetxferfailed` на файлы сверх лимита — то же поведение, что при отсутствии файла на сервере. Для реальных ресурс-листов не достижимо.
- `sv_filetransfercompression`/`.ztmp`-кэширование не изменяются; первый bz2-проход на файл остаётся (легитимная разовая стоимость).
